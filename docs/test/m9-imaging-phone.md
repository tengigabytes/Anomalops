# M9 前置：`:core:imaging` 在手機上的速度與記憶體

2026-10-01 · 狀態：CPU 參考版實測完成；FR-17 時間不達標、FR-33 六張放不進記憶體 → 2026-10-02 改成逐張累加後，FR-17 與候選 B 的記憶體不再隨張數增加（第 4 節）

`:app` 的 `experiment/ImagingBenchmark`（手機端測試，不用相機）。手機 blazer（Pixel 10 Pro），Android 17。影像是程式產生的紋理，大小 2040 × 1536，相當於 12.5 MP RAW 的半尺寸平面（`stackTool` 用的大小），只算亮度一個平面；每步一個測試，每步只量一次。溫度狀態 0（沒有降頻）。

## 1. debug 版要慢約 10 倍

一般的 debug 安裝（`DEBUGGABLE`）跑出來的時間不能用：

| 項目 | debug 版 | 非 debug 版 |
| --- | --- | --- |
| 雙線性取樣 3 M 次 | 459 ms | 41 ms |
| 整張對齊（`GlobalAligner`） | 4.3–4.5 s | 0.42–0.58 s |
| 逐塊對齊（`TileAligner`） | 10.0–10.3 s | 0.97–0.99 s |
| 單純的乘加迴圈 50 M 次 | 67–69 ms | （未量） |

- 單純迴圈在 debug 版也快，慢的是有大量小函式呼叫的程式（取樣、座標換算），推測 debug 版的即時編譯不做內聯。
- 先用 `cmd package compile -m speed` 預先編譯，debug 版仍一樣慢（對齊一張 14.6 s）。
- 非 debug 版的數字是**暫時**把 `:app` 的 debug 建置改成 `isDebuggable = false` 量的，沒有提交；量完已裝回一般的 debug 版。

## 2. 非 debug 版的結果

| 步驟 | 手機 | 桌機 JVM（`:core:imaging` README） | 其中記憶體回收 |
| --- | --- | --- | --- |
| 半尺寸解馬賽克（4080 × 3072 RAW） | 234 ms | — | 0 |
| 對齊一張（整張＋逐塊） | 1.42–1.49 s | 約 0.6–0.8 s | 0.04–0.16 s |
| FR-17 低光合成，5 張（只算亮度） | 11.8 s | 約 3.4 s | 4.0 s（31 次） |
| FR-33 候選 A，3 張（只算亮度） | 5.5 s | — | 2.7 s（27 次） |
| FR-33 候選 B，3 張（只算亮度） | 13.5 s | — | 7.5 s（90 次） |
| FR-33 候選 C，3 張 | 記憶體不足 | — | — |
| FR-33 三個候選，4 張或 6 張 | 記憶體不足 | — | — |
| 輸出成 ARGB（含陰影表） | 390 ms | 約 90 ms | 0 |

- **記憶體**：這個程序的 Java 記憶體上限是 256 MB。一個平面 12.5 MB；6 張 R、G、B 加亮度就要 300 MB，只算亮度的 6 張連同 `StackGuard` 的補洞複本與合成的中間平面也放不下，4 張也不行。
- **FR-17**：要求 12.5 MP × 5 張 ≤ 3 s。CPU 版只算亮度就要 11.8 s，三個顏色還會更久，CPU 版不可能達標；FR-17 本身就寫明 GPU 執行，ADR-0016 也說要在實機量過再決定是否先做 GPU 版，這就是那個量測。
- **FR-33**：T12 的時間目標（6 張 ≤ 10 s，提議）目前連記憶體都過不了；3 張時有一半到一半以上的時間在回收記憶體。

## 3. 對設計的影響（待維護者決定）

- 正式版不能把整組影像都以浮點數放在 Java 記憶體：可選 GPU 記憶體（FR-17 原本就要 GPU）、Java 記憶體以外的緩衝、半精度、或分塊處理。這是架構決定，宜寫 ADR。
- 之後的速度量測一律用非 debug 版；`ImagingBenchmark` 的 KDoc 已註明。
- 桌機 CPU 版仍是正確答案的基準（GPU 版要和它比對）。

## 4. 逐張累加之後（ADR-0017 第 2 步，2026-10-02）

`LowLightMerge.start` 與 `StackGuard.start`（候選 B）改成一次加入一張；`ImagingBenchmark` 每張在加入前才產生、加入後丟掉，像相機一張張送來。時間只算加入的部分（不含產生影像）。「存活的記憶體」是每步之後先做一次記憶體回收（不計時）再量，表示合成實際保留的量，不含垃圾。非 debug 版、溫度狀態 0、只算亮度，每項量一次。和第 2 節一樣用合成的紋理，結果與一次全部合成逐位元相同（JVM 測試）。

| 項目 | 張數 | 時間 | 其中記憶體回收 | 存活的記憶體（最高） |
| --- | --- | --- | --- | --- |
| FR-17 低光合成 | 3 | 6.1 s | 1.3 s | 66 MB |
| FR-17 低光合成 | 5 | 12.6 s | 4.0 s | （這次沒有量存活量） |
| FR-17 低光合成 | 6 | 15.2 s | 4.2 s | 66 MB |
| FR-33 候選 B（含 `StackGuard`） | 3 | 8.3 s | 4.8 s | 98 MB |
| FR-33 候選 B（含 `StackGuard`） | 6 | 15.6 s | 9.4 s | （這次沒有量存活量） |
| FR-33 候選 B（含 `StackGuard`） | 8 | 20.2 s | 11.0 s | 98 MB |

- 只放參考張的時候是 26 MB（含產生影像用的紋理）。FR-17 不論 3 張或 6 張都是 66 MB，B 不論 3 張或 8 張都是 98 MB：**記憶體不再隨張數增加**，6 張、8 張都不再記憶體不足。
- 時間沒有變快：FR-17 五張 12.6 s，第 2 節一次合成是 11.8 s，回收時間一樣約 4 s。回收來自每張的暫存平面（金字塔、重新取樣、鄰域平均），不是保留的影像；B 一半以上的時間仍在回收。速度要靠 GPU（第 3 步以後）。
- B 三張 8.3 s，第 2 節一次合成三張是 13.5 s。推測是同時存活的量變小，回收的負擔跟著變輕；只量了一次。
- 候選 A、C 沒有改：A 的決定（清晰度最高的張號，平滑成權重）要等全部張數到齊才知道，現在的寫法無法逐張累加（見 ADR-0017 補註），暫時仍收齊全部再合成，6 張仍會記憶體不足。
