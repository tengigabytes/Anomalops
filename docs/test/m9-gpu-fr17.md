2026-10-02 · 狀態：進行中；均方差比 CPU 快 6.8–8.5 倍；「時脈停在最低檔」已查明；重新取樣改成重複使用輸出平面後快約 3–15 倍（第 2 節）；整張對齊上 GPU，結果與 CPU 相同，快約 2.3 倍（第 3 節）；逐塊對齊上 GPU，3024 塊與 CPU 相同，快約 7.4 倍（第 4 節）；合成上 GPU，5 張 3 色一組 0.78–0.92 s，不含解碼、顏色與輸出（第 5 節）；RAW 到 ARGB 全程上 GPU，5 張 12.5 MP 一組 0.91–1.09 s（第 6 節）

手機 blazer（Pixel 10 Pro），溫度狀態 0。量法同 [m9-gpu-trial.md](m9-gpu-trial.md)：`:app` 的 `experiment/GpuBenchmark`，暫時改成非 debug 版（沒有提交，量完已裝回 debug 版），5 次取中位數。

## 1. 均方差的寫法

1. 第 3 步每個執行緒只算一點，每 256 點就要在共享記憶體做一次 8 步的加總。改成每個執行緒走 8 列（16 × 16 的工作群組），加總由 8 點分攤。其他形狀（16 × 16 走 1 或 32 列、8 × 8、4 × 4）都比較慢。
2. 第 1 點的版本，每個執行緒走的是**相鄰的** 8 列，同一批執行緒讀的列彼此相隔 16 個像素，紋理快取幾乎沒用。改成每個執行緒的 8 列彼此相隔 16 列，同一輪的 16 個執行緒讀相鄰的 16 列，時間減半（固定在高時脈下量：54 → 27 ms）。
3. 試過沒有幫助的：`textureGather` 一次取 4 個像素、拿掉 `precise`。

結果仍與 CPU 相同（相對差 ≤ 1.1 × 10⁻⁷，最佳候選相同）。非 debug 版、有前景畫面、中位數：

| 工作量 | CPU | 第 3 步 GPU | 第 1 點 | 第 2 點 |
| --- | --- | --- | --- | --- |
| 81 個候選，金字塔第 2 層（510 × 384），每點都算 | 134.3 ms | 71.4 ms | 22.6 ms | 15.7 ms |
| 27 個候選，第 0 層（2040 × 1536），每隔一點（整張對齊在第 0 層的搜尋） | 177.3 ms | — | 64.2 ms | 25.9 ms |

## 2. GPU 時脈

量法：`:app` 的 `experiment/GpuClockExperiment`，每種情境跑約 2–4 s，前後讀 GPU 的 devfreq `trans_stat`（APP 可以讀），算出這段時間在各頻率各停了多久。最低檔是 396 MHz（`min_freq`），最高 1094 MHz，調速器 `precise_ondemand`。非 debug 版、有前景畫面。

| 情境 | 每次 | 時脈分布 |
| --- | --- | --- |
| 均方差 27 個候選，每次讀回 | 31.1 ms | 分散在 396–1094 MHz，1094 MHz 占 32% |
| 同上，加 ADPF 效能提示 | 22.3 ms | 幾乎都在 512 MHz 以上，1094 MHz 占 24% |
| 重新取樣，每次等 GPU 做完 | 14.7 ms | 396 MHz 占 66% |
| 重新取樣，最後才等 | 14.8 ms | 全部 396 MHz |
| 重新取樣，加 ADPF | 12.7–13.7 ms | 幾乎全部 396 MHz |

重新取樣改成寫進重複使用的輸出平面（`PlaneKernels` 的 `into` 參數）後，與每次新配置在同一次執行中比較（2026-10-02，非 debug 版，溫度狀態 0，每種 300 次，2040 × 1536 的 32 位元平面）：

| 輸出平面 | 等 GPU 的方式 | 無提示 | 加 ADPF | 時脈分布 |
| --- | --- | --- | --- | --- |
| 每次新配置 | 每次等 | 14.8 ms | 13.3 ms | 幾乎全部 396 MHz |
| 每次新配置 | 最後才等 | 16.1 ms | 13.5 ms | 幾乎全部 396 MHz |
| 重複使用 | 每次等 | 4.2 ms | 4.3 ms | 全部 396 MHz |
| 重複使用 | 最後才等 | 1.1 ms | 1.1 ms | 約 87–91% 在 1094 MHz |

同一次執行的均方差（27 個候選）是 32.2 ms，加 ADPF 是 24.1 ms，和上表的 31.1、22.3 ms 相近。

ADPF 是 `PerformanceHintManager` 的工作階段，每次呼叫後回報實際時間，目標 16 ms。

- **之前「時脈多半停在 396 MHz」是量法的問題**：之前每 0.05 s 讀一次 `cur_freq`，取樣期間包含 GPU 閒著的時間。GPU 真的在忙時（均方差）會升到 1094 MHz。
- **均方差慢的主因是紋理快取**（第 1 節第 2 點），不是時脈。
- **ADPF 提示讓均方差再快約 1.4 倍**，時脈較高、較穩定。
- **重新取樣慢的主因是每次新配置輸出紋理**：改成重複使用後，每次等 GPU 的情況從 14.8 ms 降到 4.2 ms，最後才等的情況從 16.1 ms 降到 1.1 ms。兩者相減，配置的成本每次約 9–15 ms，加 ADPF 也只少 1–3 ms。
- **每次都等 GPU 做完，時脈就停在最低檔**：重複使用平面但每次等，全部在 396 MHz，每次 4.2 ms；最後才等，時脈升到 1094 MHz，每次 1.1 ms。推測每次等待之間 GPU 閒著，調速器看到的使用率低。ADPF 對這兩種情況都沒有影響（4.2 → 4.3 ms，1.1 → 1.1 ms）。
- 因此合成程式的寫法：輸出與中間平面事先配置、重複使用；連續的核心只在需要讀回 CPU 時才等 GPU（例如均方差的結果）。
- 推測：照現在的速度，一張的整張對齊加逐塊對齊在 GPU 上約 0.15–0.3 s，四張約 0.6–1.2 s，FR-17 的 3 s 還有空間給合成、顏色與輸出，但要等第 4 步做完才能確定。

## 3. 整張對齊

寫法：`GlobalAligner` 的搜尋與 `GaussNewton` 的迭代改成由呼叫端提供「代價」與「法方程式」兩個函式（CPU 結果不變，JVM 測試通過）。GPU 版 `GpuGlobalAligner` 直接用同一份搜尋與迭代程式，只有加總在 GPU 上：均方差核心、新的 `GaussNewtonKernel`（一輪的 9 個和，寫法同均方差，讀回緩衝重複使用）、`GpuPyramid`（下一張的金字塔寫進同一組平面）。

正確性（`:core:gpu` 的 `GpuGlobalAlignerTest`，debug 版，2040 × 1536，±40 雜訊，真值縮放 1.006、位移 (13.4, −7.7)）：法方程式與 CPU 的 `GradientSums` 最大相對差 1.4 × 10⁻⁷；整張對齊結果與 CPU 相同（1.0060012、13.400172、−7.700603），與真值差：縮放 1.2 × 10⁻⁶、位移 0.0006 px。

速度（`:app` 的 `experiment/GpuAlignBenchmark`，非 debug 版，有前景畫面，溫度狀態 0，同一個場景，真值 1.006、(−13.3, 7.7)；CPU 與 GPU 結果相同）：

| 項目 | 中位數 | 最快 |
| --- | --- | --- |
| CPU：這一張的金字塔＋整張對齊 | 241.1 ms | 237.6 ms |
| GPU：上傳這一張 | 6.4 ms | 3.6 ms |
| GPU：這一張的金字塔（重複使用平面） | 1.6 ms | 1.3 ms |
| GPU：整張對齊 | 105.1 ms | 81.4 ms |

- GPU 只快約 2.3 倍（241.1 ÷ 105.1）。推測：搜尋每一層、高斯牛頓每一輪都要讀回 CPU 才能決定下一步（6 層加最多 8 輪），每次都等 GPU，時脈停在低檔（第 2 節）。可能的改法：ADPF 提示，或在 GPU 上直接選出最佳候選；都還沒量。

測試場景（2026-10-02 維護者決定）：

- 原本的紋理是 400 × 300 的隨機格放大到 2040 × 1536（每格約 5 px），只有細紋理，金字塔最上層（63 × 48）幾乎是平的。位移 (−13.3, 7.7)、縮放 1 時，CPU 和 GPU 都對到縮放 1.0151561、位移 (−9.0, 9.0)。
- 原因在最上層的窮舉：位移格點是 32 px，真值落在格點之間；正確位置的代價 11762，選中的縮放 1.02、位移 (0, 0) 是 15250，正確位置不在格點上所以沒被選到。往下每層只找 ±1 步，回不來；高斯牛頓往真值走，但超過 2 px 的漂移上限，退回起點。換回修改前的 CPU 程式結果相同，是原本演算法的行為。
- 決定：演算法不動，測試改用各尺度都有紋理的場景（256、64、16、4 px 的隨機格各一份，雙線性），之後以實拍連拍確認。JVM 上試 6 組縮放與位移（含上面失敗的那組）全部對準，位移誤差 ≤ 0.001 px，縮放誤差 ≤ 1.2 × 10⁻⁶。
- 推測：只有細紋理的實景（例如沙地、懸浮物）可能遇到同樣的情況，實拍時要特別看。

## 4. 逐塊對齊

寫法（`GpuTileAligner`，著色器在 `TileShaders`）：一個工作群組（256 個執行緒）負責一塊，在 GPU 上跑完這一塊的整個搜尋（第 2 層 ±2 步、第 1 層與第 0 層各 ±1 步）、兩個拋物線與最後的代價，所以一張只要一次派送、一次讀回。每塊的紋理量與「可信」門檻（中位數乘比例）只跟參考張有關，每張參考張算一次。

正確性（`:core:gpu` 的 `GpuTileAlignerTest`，debug 版，第 3 節的場景，另有一塊區域自己再移動 (3.4, −2.2)，兩邊用同一個整張變換）：3024 塊中選到不同整數位移的 0 塊；其餘次像素差最大 4.8 × 10⁻⁷ px，代價最大相對差 5 × 10⁻⁶，紋理最大相對差 1.5 × 10⁻⁷，可信判定不一致 0 塊。

速度（`GpuAlignBenchmark`，非 debug 版，有前景畫面，溫度狀態 0；兩邊的平均殘差相同、3024 塊都可信）：

| 項目 | 中位數 | 最快 |
| --- | --- | --- |
| CPU：整張對齊（含這一張的金字塔） | 241.2 ms | 236.9 ms |
| CPU：逐塊對齊 | 557.2 ms | 548.9 ms |
| GPU：上傳這一張 | 5.5 ms | 5.1 ms |
| GPU：這一張的金字塔 | 1.4 ms | 1.3 ms |
| GPU：整張對齊 | 93.5 ms | 64.0 ms |
| GPU：逐塊對齊 | 75.7 ms | 67.2 ms |

- 逐塊對齊快約 7.4 倍（557.2 ÷ 75.7）；一張的對齊合計 CPU 約 798 ms、GPU 約 176 ms。推測四張約 0.7 s，與第 2 節的估計（0.6–1.2 s）相符。
- 觀察與更正：自己移動的那塊區域，原本估出的平均殘差是 (3.133, −2.005)，設定是 (3.4, −2.2)，CPU 與 GPU 相同；原先推測是次像素拋物線把小數拉向整數。2026-10-02 在 JVM 上查明主要是測試的算法：移動區域是畫面（frame）座標，測試卻依參考張座標挑塊，整張變換把邊上的塊推到區域外一半，混進沒動的內容。改成只算在畫面座標中整塊落在區域內的 45 塊，平均是 (3.390, −2.186)，差 0.010、0.014 px。`GpuTileAlignerTest` 已改成這樣算（待實機重跑）。
- 拋物線的偏差本身（JVM，512 × 384，只有整體位移、已知整張變換，各塊平均）：本場景（最細 4 px 格）位移 0.1–0.9 px 時偏差最多 0.024 px（0.2 → 0.177、0.8 → 0.823），往整數靠；最細 8 px 格最多 0.013 px，最細 16 px 格最多 0.010 px；`SyntheticScene` 的高斯斑點最多 0.003 px（無雜訊）。偏差隨細紋理變大，量級是百分之一到二像素。

## 5. 合成

寫法（`GpuLowLightMerge`，著色器在 `MergeShaders`）：照 `LowLightMerge` 逐張累加。每張先在 GPU 上對齊（第 3、4 節），再兩次派送：一次算這一張亮度在對齊位置與參考張的差（`OffsetField` 的位置：整張變換加上塊中心之間內插的殘差），一次以 3 × 3 平均差算權重 exp(−d² ÷ 容許量)，把權重與各色版的加權值加進 GPU 上的累加平面（R32F，可讀寫）。結束時就地除以權重和。顏色最多 3 個色版。

正確性（`:core:gpu` 的 `GpuLowLightMergeTest`，debug 版，參考張加 2 張，其中 1 張有自己移動的區域，亮度加一個衍生色版，逐張與 CPU 比對）：兩張的整張對齊與 CPU 相同；合成結果最大相對差 6.4 × 10⁻⁶（亮度）與 5.7 × 10⁻⁶，超過 10⁻⁶ 的像素 380 與 338 個（共 313 萬），NaN 不一致 0。差異來自 GPU 的 `exp` 與浮點捨入。雜訊（`estimateNoise`）從參考張的 31.95 降到 16.20。

速度（`:app` 的 `experiment/GpuMergeBenchmark`，非 debug 版，有前景畫面，溫度狀態 0）：一組 5 張，每張上傳亮度與 3 個色版（色版由亮度衍生），逐張加入。同一組跑 3 次：

| 項目 | 第 1 次（含編譯） | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 開始（參考張的金字塔、累加平面） | 71.8 ms | 41.3 ms | 50.3 ms |
| 每張上傳 4 個平面 | 16.2–29.7 ms | 17.6–37.3 ms | 22.2–32.8 ms |
| 每張加入（對齊＋合成） | 138.3–163.8 ms | 164.0–189.8 ms | 169.0–187.6 ms |
| 結束 | 4.1 ms | 8.9 ms | 9.4 ms |
| 一組合計 | 779.0 ms | 887.5 ms | 916.0 ms |

- FR-17 的上限 3 s；這裡 0.78–0.92 s，但不含 RAW 解碼成平面、顏色轉換與輸出。CPU 版只算亮度的 5 張是 11.8–12.6 s（[m9-imaging-phone.md](m9-imaging-phone.md)）。
- 觀察：第 1 次（含編譯著色器）反而最快，後兩次每張加入多約 20–30 ms。原因未查；溫度狀態前後都是 0。推測與 GPU 時脈或記憶體有關，要用 `GpuClockExperiment` 的量法才能分辨。

## 6. 解碼與輸出

寫法（`GpuDevelop`，著色器在 `DevelopShaders`）：

- 解碼：RAW_SENSOR 以 16 位元整數紋理（R16UI）上傳，列尾補齊以 `GL_UNPACK_ROW_LENGTH` 處理；每個 2 × 2 格在 GPU 上照 `Demosaic.halfSize` 算出 R、綠的平均、B，再照 `Rgb.luma` 算亮度，寫進四個可重複使用的平面。減黑位、除以（白位 − 黑位）改成在 CPU 上先做成表（每個格位置 65 536 個值，黑白位改變才重做），GPU 查表：在著色器裡做這個除法時，紅色平面 313 萬個值有 212 萬個與 CPU 不同。
- 輸出：照 `Render.toArgb` 逐像素做剪切判斷、陰影表、白平衡、色彩矩陣、曝光、高光往中性灰、色調曲線，sRGB 編碼用和 CPU 相同算式產生的 65 536 格查表，寫成 ARGB 讀回。
- 解析度是半尺寸（12.5 MP 的 RAW 合成出 3.1 MP），同 `StackTool` 的預設。FR-17 沒有寫輸出解析度；2026-10-02 維護者決定先用半尺寸。

正確性（`:core:gpu` 的 `GpuDevelopTest`，合成的 4080 × 3072 GBRG RAW，列尾補齊、各格黑位不同、部分剪切，33 × 25 陰影表）：解碼的四個平面與 CPU 完全相同；輸出 313 萬像素中 34 個差 1 個色碼，其餘相同（提議上限：0.1% 的像素、差 1）。

速度（`:app` 的 `experiment/GpuRawPipelineBenchmark`，非 debug 版，有前景畫面，溫度狀態 0）：5 張 4080 × 3072 RAW 先做好放在記憶體（如同 FR-62 環形緩衝裡的一組），從上傳一路到 ARGB 讀回。同一組跑 3 次：

| 項目 | 第 1 次（含編譯） | 第 2 次 | 第 3 次 |
| --- | --- | --- | --- |
| 每張上傳＋解碼 | 12.2–68.2 ms | 17.0–29.7 ms | 19.9–27.5 ms |
| 開始 | 71.6 ms | 47.9 ms | 66.5 ms |
| 每張加入（對齊＋合成） | 156.1–176.3 ms | 179.9–217.1 ms | 198.8–226.7 ms |
| 結束 | 5.1 ms | 5.7 ms | 5.4 ms |
| 輸出並讀回 ARGB | 24.2 ms | 29.5 ms | 33.5 ms |
| 一組合計 | 914.3 ms | 983.4 ms | 1088.4 ms |

- FR-17 上限 3 s，目前 0.91–1.09 s（半尺寸輸出）。不含：從相機取得 RAW、輸出後的編碼與存檔。
- 同一輪先跑的對齊計時，CPU 參考值是 243.8 ms、574.8 ms，與第 4 節的 241.2 ms、557.2 ms 相近，表示手機狀態正常。前一輪 CPU 參考值是 419.5 ms、960.6 ms，整體慢約 1.7 倍，那一輪的數字不採用；原因未查（兩輪的電量都是 38–39%，溫度狀態都是 0）。
- 與第 5 節相同，後面幾次比第 1 次慢（每張加入多約 20–50 ms），原因未查。

## 7. 還沒做的（第 4 步）

全尺寸輸出（目前先用半尺寸）。從相機取得 RAW 到存檔的整段時間（接上 `:app` 時）。整張對齊每次讀回都等 GPU 的問題（第 3 節）：在 GPU 上選最佳候選可減少讀回，但搜尋就不再與 CPU 共用、不能逐位元比對；2026-10-02 維護者決定暫不做，等整體計時出來再看。正式版的合成要不要用 ADPF 提示，到時一併決定。實拍連拍確認整張對齊在細紋理畫面上的表現。逐塊對齊次像素偏向整數，最多約 0.024 px（第 4 節），要不要處理待維護者決定。同一組連續重跑時後面幾次較慢（第 5、6 節）。
