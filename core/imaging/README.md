# :core:imaging

多幀影像處理（ADR-0016）。純 Kotlin/JVM 模組，不依賴 Android 與其他專案模組，單元測試可在任何環境執行。

| 項目 | 內容 |
| --- | --- |
| 職責 | RAW 解成線性 RGB、同一組連拍的對齊、景深合成（FR-33）、低光多幀合成（FR-17）；之後的超解析（FR-18、FR-19） |
| 依賴 | 無 |
| 被誰使用 | `:core:gpu`；`:app` 的合成開關（FR-17，預設關）。FR-33 尚未接上 |
| 對應需求 | FR-17、FR-33（ADR-0015） |
| 內容 | `align/`：`Plane`（單通道線性數值、雙線性取樣、減半；`fromBayer` 由 RAW 的 2 × 2 格合成亮度）、`Pyramid`、`Similarity`（以畫面中心縮放加位移）、`GlobalAligner`（整張的縮放與位移，由粗到細窮舉；搜尋本身另有一個以函式傳入代價與法方程式的版本，`:core:gpu` 共用）、`GaussNewton`（整張的次像素求精；均方差的拋物線擬合在雜訊或清晰度不同時有偏差，見 ADR-0015 補註；法方程式在 CPU 上由 `GradientSums` 計算）、`TileAligner`（每 32 像素一塊的殘差位移、代價與紋理可信度）、`FrameAligner`（對外入口：一次建好參考影像的金字塔，逐張對齊；`warp` 依整張變換重取樣） |
| 內容（解碼） | `develop/`：`CfaLayout`（執行時讀的色彩排列）、`RawFrame`（RAW_SENSOR 樣本、各格黑位、白位）、`Demosaic.halfSize`（每格一個 RGB，快）與 `Demosaic.bilinear`（全尺寸）、`ColourPipeline`（白平衡增益加色彩矩陣，ADR-0002）、`Rgb.luma`（Rec. 709 亮度） |
| 內容（輸出） | `develop/`：`Render.toArgb`（ADR-0015 最後一步：相機 RGB → 8-bit sRGB ARGB；依序為 RAW 接近剪切的程度、鏡頭陰影補償、白平衡、色彩矩陣、曝光、高光往中性灰混合、以最亮色版套色調曲線（保持色相）、sRGB 編碼）、`RenderOptions`（曝光、高光起點 0.9、曲線肩部 0.9、白點 2；都是提議值，外觀未定）、`ShadingMap`（`STATISTICS_LENS_SHADING_CORRECTION_MAP` 的四色版增益格點，雙線性內插；RAW 是否已補償、2× 裁切串流的對應範圍待實機確認） |
| 內容（視野） | `align/FieldOfView`：從 RAW 成像的畫面裡，找出相機自己那張成品所涵蓋的範圍。相機的成品與預覽是 RAW 畫面正中央的一塊，相機沒有回報這個範圍（`SCALER_CROP_REGION` 回報的是整個感光元件），主鏡頭的比例還會隨對焦距離變。做法是把兩張縮到約 250 像素寬、各自正規化後以 `GlobalAligner` 找縮放與位移；配不上（太暗、沒紋理、結果不像置中裁切）回傳 null。Pixel 10 Pro 實測（2026-10-03）：超廣角感光元件 84.8–85.2%，主鏡頭 88.6–95.0% |
| 內容（連拍的前置） | `merge/BurstReference`（從 RAW 樣本直接算每張的清晰度，挑最清晰的當合併的參考張）、`develop/NoiseProfile`（感光元件的雜訊模型 `SENSOR_NOISE_PROFILE`：變異數 = 係數 × 亮度 + 常數；換算成半尺寸亮度平面的雜訊標準差給 `LowLightMerge`；`chromaSigma` 預測成像後單張的色彩雜訊（色階），2026-10-03 五組實拍與量到的差 −12% 到 +34%。2026-10-03 以腳架上兩張的差實測，ISO 155 與 ISO 333 都在 4% 以內）、`RawFrame.cell`（單一 2 × 2 格的半尺寸解馬賽克） |
| 內容（外觀） | `develop/`：`ChromaDenoise`（成像後的色彩降噪：每個像素的顏色（各色版減亮度）改成鄰近像素顏色的加權平均，權重看距離、亮度是否相近、顏色是否相近（顏色的容許差 `RenderOptions.chromaTolerance`，每輪收窄為 1、0.5、0.3 倍；比容許差淡的顏色細節會跟雜訊一起被平均掉，所以容許差要跟著雜訊走），所以顏色不會越過邊緣、也不會在亮度相同的兩種顏色之間暈開，亮度不動；最多三輪，每輪取 5 × 5 個鄰點、間距 2、4、8 像素；全部整數運算，GPU 版逐位元相同；由 `RenderOptions.chromaPasses` 啟用，預設 0。2026-10-03 實拍：5 張合成的色彩雜訊約為原生相機的 20 倍、亮度雜訊相當，三輪後降到約十分之一；同日加上顏色相近的權重，以 4 × 4 區塊平均量（不計雜訊），顏色被移動超過 10 個色階的區塊由 0.7–1.1% 降到 0.5%，平坦區的雜訊不變）、`Saturation`（成像後的飽和度：每個色版離該像素亮度的距離乘上倍率，亮度與灰色不變；整數運算，GPU 版逐位元相同；由 `RenderOptions.saturation` 啟用，預設 1。2026-10-03 以 8 × 8 區塊平均量（不計雜訊），合成圖的飽和度比相機成品低 31–38%）、`Sharpen`（成像後的銳化：8-bit 畫面的亮度減去 5 × 5 二項式模糊，乘上銳化量加回三個色版；全部整數運算，GPU 版逐位元相同；由 `RenderOptions.sharpen` 啟用，預設 0）、`AutoLook`（由參考張的 RAW 決定曝光增益與銳化量，在 CPU 上算，CPU 與 GPU 流程共用：以相機回報的 RAW 後增益（`CONTROL_POST_RAW_SENSITIVITY_BOOST` ÷ 100，超過感光元件最高類比感光度後 RAW 沒乘到的那一段）為下限，亮場景再由畫面亮度的中位數往上補、有上限；不知道這個增益時只用中位數；只提亮不壓暗；增益越高銳化越少）、`LookOptions`（中位數目標 0.19、有相機增益時不再往上補（上限 1；曾試 2.5，深色主體會發灰）、不知道相機增益時上限 8、銳化 0.5、增益 3 到 8 之間銳化遞減到 0、色彩降噪三輪、飽和度 1.25（三種模式都選 1.25 而不是 1.5，各一次；自動模式有一次選不調而不是 1.25）、色彩降噪跟著預測的色彩雜訊（`NoiseProfile.chromaSigma` ÷ √張數）：1.5 個色階以下不做、4 以上用完整的容許差 40、中間線性；固定 40 時光線好的場景（ISO 117，預測 1.5）紙上很淡的紅色印章被濾掉，維護者指出，該場景選不濾波；兩個暗場景（預測 5.9、7.0）選容許差 40 而不是 15–17；兩端是提議值，中間的一個場景（預測 1.9，算出 6.6）選它而不是不濾或 40；都是提議值，依 2026-10-03 維護者在兩個室內場景的左右對照選擇，樣本很少） |
| 內容（景深合成） | `stack/`：`FocusStack` 介面（以亮度決定、各色版照同一決定合成），ADR-0015 的三個候選：`ContrastSelectStack`（A，局部對比選取加平滑）、`LaplacianPyramidStack`（B，拉普拉斯金字塔逐層取最大係數）、`GuidedWeightStack`（C，引導濾波修整權重）；`StackGuard`（合成不比最清晰的單張清楚時退回單張，缺的像素以參考幀補；`start` 回傳 `Session`，可逐張加入）；`FocusAccumulator`（逐張加入、最後 `finish`，ADR-0017）：B 逐張累加（每層保留目前最高分與各色版的係數），A 分兩輪（第一輪只留每像素的最高分與張號，第二輪再加入每張乘上平滑後的權重；2026-10-02 維護者決定），兩者記憶體都不隨張數增加；C 的權重要看全部張數，暫用 `CollectingAccumulator` 收齊再合成；`Filters`（拉普拉斯、盒狀平均、引導濾波、放大） |
| 內容（低光合成） | `merge/`：`LowLightMerge`（`start` 回傳逐張累加的 `Accumulator`，只保留參考張、累加和與當下這張，ADR-0017；FR-17 第一階段：逐張對齊後，依 3 × 3 鄰域與參考幀的差距相對雜訊給權重，差太多的像素幾乎不計入，避免移動的魚留下重影；`estimateNoise` 由拉普拉斯的中位絕對值估雜訊）、`OffsetField`（整張變換加上在塊中心之間內插的殘差位移） |
| 桌機工具（T12） | 測試資料夾的 `tool/`：`StackTool`（手機拉回的 DNG 依序解馬賽克、以中間那張為參考對齊、A／B／C 三個候選各合成一次並經 `StackGuard`、輸出 PNG 與最清晰的單張，印出時間與判定；`--lowlight` 改跑 FR-17（以最清晰的一張為參考，印出每張的對齊結果，另輸出只用整張對齊與不對齊直接平均的對照圖）、`--full` 用全尺寸、`--auto` 以 `AutoLook` 決定亮度與銳化、`--exposure=` 指定增益、`--chroma=` 與 `--tolerance=` 指定色彩降噪的輪數與容許差、`--dump` 另存線性資料供桌機試外觀）、`DngReader`（`DngCreator` 寫的未壓縮 Bayer DNG：黑白位、AsShotNeutral、D65 的 ForwardMatrix、OpcodeList2 的 GainMap 陰影表、NoiseProfile）。執行：`gradlew :core:imaging:stackTool --args="<輸出資料夾> <a.dng> <b.dng> ..."`。不進 APP；放在測試資料夾、不另開模組（2026-10-01 維護者同意）；尚未用手機的實拍 DNG 跑過 |
| 參數 | `AlignOptions`：最大位移 64 像素、縮放 ±3%、塊 32 像素、塊內搜尋 ±8 像素、紋理門檻為中位數的 0.1；都是提議值，待微距待測清單 T9、T10 的實拍資料修正 |
| 測試 | `LowLightMergeTest`：逐張累加與一次合成逐位元相同；5 張帶手晃與雜訊的合成連拍，雜訊標準差 6.01 → 2.01（FR-17 要求降 ≥ 50%）；一隻每張多游 6 像素的魚，合成後魚的位置與參考幀差 4.81、與單純平均差 11.66（沒有重影）；雜訊估計、色版跟隨亮度<br>`FieldOfViewTest`：置中 85% 的裁切在色調不同、有雜訊時仍找得到（誤差 0.5% 以內），較小與偏心的裁切、同一張圖得到整張，平坦或無關的畫面回傳 null<br>`BurstInputsTest`：最清晰的一張被選為參考、`RawFrame.cell` 與 `Demosaic.halfSize` 相同、雜訊標準差照模型（含一半亮一半暗的畫面取平均變異數）、與實際加進去的雜訊相符<br>`ChromaDenoiseTest`：平坦與灰階畫面不變、色彩雜訊降到五分之一以下而亮度最多動 2 個色階、亮度差很大的兩種顏色不互相暈開、亮度相同的兩種顏色也不互相暈開、權重表與間距、`Render.finish` 先降噪、再調飽和度、再銳化<br>`SaturationTest`：倍率 1 與灰色不變、手算值、不剪切時亮度不動、強烈的顏色剪切而不繞回<br>`SharpenTest`：平坦畫面與銳化量 0 不變、階梯邊緣的手算值（±16 個色階）、不超出 0–255、三個色版加同樣的量、`Render.toArgb` 帶銳化等於先成像再銳化<br>`AutoLookTest`：增益把中位數拉到目標、亮的畫面不壓暗且銳化全量、很暗的畫面停在增益上限且不銳化、中位數跟著白平衡增益、色彩矩陣與陰影表、小面積亮區不影響中位數、相機的 RAW 後增益是下限且只有亮場景會超過它、色彩降噪照預測的雜訊與張數（低於下限不做、中間取一半容許差、高於上限或沒有雜訊模型用完整容許差）<br>`RenderTest`：sRGB 編碼標準值、色調曲線（肩部前不變、肩部斜率 1、白點為 1、單調）、中間調照增益與矩陣通過、全剪切的高光成中性白、肩部保持色相、負值歸零、陰影表的雙線性內插與邊界、陰影補償在剪切判斷之後、灰色 RAW 端到端<br>`DngReaderTest`：合成的 DNG（GBRG、各格黑位、AsShotNeutral、兩組 ForwardMatrix、四張 GainMap）讀回、ForwardMatrix 換算後白色仍是白色、`StackTool` 對三張合成 DNG 寫出四張 PNG<br>`DemosaicTest`：四種色彩排列、各格黑位、純色還原、平滑色場的雙線性誤差、白平衡與矩陣的順序、亮度權重<br>`FocusStackTest`：逐張累加與一次合成逐位元相同（三個候選；`StackGuard` 搭配 A、B）；斜放主體的合成包圍（5 張，各自清晰於一段深度），三個候選都要把誤差壓到最清晰單張的一半以下，加雜訊時要壓到四分之三以下；相同影像不變、色版跟隨亮度、`StackGuard` 保留好的合成與退回單張、補缺像素<br>`PlaneTest`：Bayer 合成與無號讀取、雙線性取樣、減半、金字塔座標換算、拋物線；`FrameAlignerTest`：以 `SyntheticScene`（解析式的高斯斑點場景，可渲染任意縮放、位移、模糊、局部移動）驗證相同影像、次像素位移、接近搜尋上限的大位移、焦點呼吸的縮放、模糊的景深合成幀、只差雜訊的靜止兩張、模糊參考張對清晰影像（後兩項在舊的拋物線求精上會失敗）、移動主體只出現在它的塊、`warp` |
| 速度 | 桌機 JVM，2040 × 1536（12 MP RAW 的亮度平面）：建參考金字塔約 31 ms，對齊一張約 0.82 s（2026-10-01 改用高斯牛頓後，另一個 6000 斑點的場景新舊都約 0.6 s）；6 張單色版景深合成 A 約 0.52 s、B 約 0.88 s、C 約 1.33 s；FR-17 低光合成 5 張單色版約 3.39 s；`Render.toArgb` 一張（含陰影表）約 90 ms（2026-10-01，各一次量測）。FR-17 要求手機上 12.5 MP × 5 張 ≤ 3 s，桌機的 CPU 版已超過，正式版要走 GPU；手機（非 debug 版，2026-10-01，[m9-imaging-phone.md](../../docs/test/m9-imaging-phone.md)）：對齊一張約 1.4 s、FR-17 五張只算亮度 11.8 s，FR-33 四張以上超出 256 MB 記憶體 |
